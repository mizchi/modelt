# 0003: 時間バジェットと実行カーネル

実行前に固定する計画。時間予算による worker 数・深さの選択と、Rust 化の効果を別々に測る。

- 純粋な planner に、時間・メモリ・worker 上限・深さ上限と、workload ごとの実測 profile を渡す。起動費用と状態保持費用を含めて選択する。推定容量を実際の時間保証に読み替えない。
- 検査 worker の並列度と、対象 API の同時操作数を分ける。対象の同時操作2/3・各2段階の schedule を列挙し、深さ・ノード数・soft deadline で打ち切った部分を未検査として返す。実行中の同期処理を強制終了しない。
- Node の worker 1/2/4 を比較する。初回起動と再利用時を分ける。実測 profile のない workload に、別の workload の測定値を流用しない。
- Rust 比較は有限グラフに限定。counterModel の56状態を TS でコンパイルし、有効操作の順序、操作 ID、遷移先を固定する。TS の動的モデル、同じ表を使う TS、Rust native、Rust Wasm を比較し、表現の最適化と実装言語の差を分ける。
- Rust に任意の TS クロージャ、TLA+ パーサー、Z3 ソルバー全体を移植したとは扱わない。Wasm はブラウザでも実行し、同じ操作列の生成と故障版・正常版の再生を確認する。
- seed 61〜100で操作列と結果を照合する。性能は512操作と65,536操作、各8回を1 batch、warmup 3 batch、測定7 batch。測定順は交互に変える。checksum と結果の一致を必須にし、機械依存の速度に合否閾値を設けない。
- 起動、表の構築・転送、カーネル、JS/Wasm 境界、SUT/オラクル照合を分けて記録する。kernel の速度から、ツール全体の速度向上を結論しない。

判断は移植範囲と利用条件を伴う提案にする。小さいジョブで worker や native 起動が支配的なら単一 worker を選び、長時間・再利用の条件では別に評価する。欠けた結果、打ち切り、意味論の不一致を成功として集計しない。
