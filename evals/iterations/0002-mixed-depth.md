# 0002: 短い履歴と長い履歴を混ぜる

0001 で長い履歴は drop 無視を追加検出したが、配信順序の検出に後退があった。短いケースと長いケースを交互にし、同じ512操作予算で比較する。

条件は [plan](../plans/0002-mixed-depth.json)。最大深さ16の半分である8から始め、8→16→8→16と交互に生成する。残り予算が足りない最後のケースは短くする。モデルの有効操作を選ぶ PRNG と故障条件には手を加えない。

開発用 seed 1〜20は既知。確認用 seed 41〜60はこの仮説の確認に初めて使う。確認結果をもとに調整して同じ確認用 seed へ再適合させない。

## 結果

[開発 run](../runs/0002-development/result.json) と [確認 run](../runs/0002-confirmation/result.json) は検出数の集計で `improved`。両 run の plan・ソースの digest は一致した。正常対照・有効操作・反例再現の失敗はない。

| 故障            | 開発: uniform→混在 | 確認: uniform→混在 |
| --------------- | -----------------: | -----------------: |
| 永続化漏れ      |              20→20 |              20→20 |
| 重複処理        |              20→20 |              20→20 |
| 3回目のリトライ |              20→20 |              20→20 |
| 配信順序の無視  |              14→15 |              12→14 |
| drop の無視     |              14→18 |              11→17 |

確認用で配信順序は3 seed を追加検出し、seed 55を見逃して計2件増加。drop 無視は6 seed の追加検出、見逃しの増加はない。故障別の合計では後退はないが、全 seed での優越ではない。

同じ512操作のもとで正常版の reset 数中央値は57→40。配信順序の最初の反例長中央値は5.5→7、drop は7→9、永続化漏れは7→10。縮小前の反例が長くなるコストは残っている。

0001 と0002は確認用 seed が異なる。混在が固定16より優れるとはこの確認実験からは結論しない。各 iteration では同じ seed の uniform-8 との比較を使った。

## 判断と次の仮説

混在方式は実験の候補として保持する。既知の人工故障では追加検出が確認できたが、seed 単位の後退と診断の長さがあるため、コア API や本番の既定手法へ自動で昇格させない。

次は探索方式を固定し、発見後の反例縮小が調査をどれだけ短くするか、追加の SUT 操作数を含めて測る。また、実リポジトリの過去バグ・修正版の対照を追加し、人工例で得た効果が移るかを評価する。確認用 seed 41〜60は使用済みとして残す。
