# 0003: 実行時間と Rust 化

[事前計画](../plans/0003-runtime.md) に従い、Node 24.22.2 / Rust 1.98.0 / macOS arm64で測定した。[生データ・profile・実行順序](../runs/0003-runtime/) を保存している。有限モデル56状態・432遷移のカーネルの比較であり、ツール全体や全モデルでの速度を保証するものではない。

## 実装言語と表現を分ける

warmup 3 batch、測定7 batch、各 batch は同じ条件を8回実行。順序を反転して比較し、checksum の不一致は0。

| 実装        | 512操作×8 全体中央値 | 65,536操作×8 全体中央値 | 大きい batch のカーネルのみ |
| ----------- | -------------------: | ----------------------: | --------------------------: |
| 動的 TS     |              2.140ms |               261.354ms |                   261.354ms |
| 表形式 TS   |             0.0202ms |                 2.503ms |                     2.503ms |
| Rust Wasm   |             0.0198ms |                 2.274ms |                     2.274ms |
| Rust native |              1.550ms |                 3.544ms |                     1.582ms |

動的表現から表形式への変更が大きく、表形式 TS と Rust Wasm の差は小さい。native の計算部分は速いが、毎回プロセスを起動する場合は起動・入出力の費用が上回った。

512操作の生成・trace 取り出し・SUT/オラクル比較まで含む中央値は、動的 TS 0.977ms、表形式 TS 0.666ms、Rust Wasm 0.700ms。照合部分が約0.66〜0.67msを占め、カーネルだけの改善が全体の同率の改善にはならない。表構築4.73msと Wasm 初期化・転送0.83msはこの warm 実行とは別。Wasm は21,306 bytesだった。

**判断:** 全面 Rust 化は現時点で採用しない。共通の有限モデル IR とデータ表現の最適化を優先する。Rust は、その後も CPU・メモリが支配的な部分で、長いセッションや再利用を条件に評価を続ける。大きいモデルや実際の分散実装での評価は別途必要。

## バジェットと実行順

`planBudget` は実測 profile と時間・メモリ・worker・深さの上限から設定を選ぶ。再利用 pool の profile を含む記録では、10/100/1000msで4 worker、深さ21/24/28が選ばれた。これは既に pool がある状態のカーネル推定であり、新規プロセスの起動時間やモデル検査全体の計算量を表す値ではない。

小さい非同期 counter では単一実行が選ばれた。2同時操作の6順序は1msの予算で検査し、4順序の lost update を検出。3同時操作では1/10msの保守的な木の上界が深さ3/5を選び、完了する履歴に達せず未検査となった。100msでは深さ6、90順序を検査し、84順序の違反を検出した。

保存した profile から新規 pool のみで計画し直すと、10msは1 worker・深さ19、100msは4 worker・深さ24、1000msは4 worker・深さ28となる。pool の初期化は約20〜24msだった。再利用できるかどうかで並列度の選択が変わることを確認した。

この割り当て例のノード数は、仮想的な二分木を streaming カーネルの work 単位へ換算した見積り。56状態のモデルに大量の固有状態が存在するという意味ではなく、visited 集合や property checker のメモリ・CPU費用は別 profile で測る必要がある。

後者の実行自体は約3.74msであり、現在の保守的な planner は小さい予算を十分活用できていない。次は「完全な幅を優先する検査」と「反例を早く探す検査」を分け、部分探索では有用な最小深さを確保する方式を評価する。未検査を合格に置き換える緩和は行わない。

## クラウド分割

task ID・manifest・source version を持つ sharding と4 runner の workflow を追加した。欠落、同じ結果の再試行、不一致を区別する。クラウドでの起動・転送・待ち時間は、このローカル性能値に含まない。クラウドの並列度はインスタンス内の worker 並列度と別に制限する。

[ローカルの独立4プロセスの記録](../runs/0003-cloud/) では29/28/36/43 taskに分割し、136/136を集約した。40 kernel は参照実装と一致し、96 schedule の正常対照が通過、故障版で88件の違反を検出した。1 shard を除くと43 task不足の `partial`、29 taskを二重配送すると重複排除して136件の `complete` になった。

100msの profile から3同時操作・深さ6・90 schedule の manifest を作り、90/90を実行した。10msでは深さ5となり、完了する schedule がないため manifest の準備を `budget-exhausted` で止めた。このローカル検証は実際のクラウドの待ち時間や転送費用の測定ではない。
