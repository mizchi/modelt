# 0001: 長い履歴を同じ予算で探索する

状態網羅の witness が3回目のリトライと drop 無視を見逃したため、履歴長を改善の変数にする。

事前条件は [plan](../plans/0001-longer-walk.json)。変更するのは1ケースの上限8→16のみ。SUT の reset/step の上限512、参照モデル、故障集合、PRNG を変えない。新しいコア API は追加しない。

開発用 seed は1〜20、確認用は21〜40。確認実行は開発実行の plan / 実装 fingerprint を照合し、途中で実装や条件を変えた場合は拒否する。再試行には新しい run ID を使う。

検出数が増えても reset・診断・縮小・確認実験のコストを含めて解釈する。seed ごとの後退や故障ごとの後退を記録し、数値を合わせるための条件変更は行わない。

## 結果

[開発 run](../runs/0001-development/result.json) と [確認 run](../runs/0001-confirmation/result.json) はどちらも `mixed`。ソース・plan の digest は両 run で一致した。正常対照・有効操作・反例再現の失敗はない。

| 故障            | 開発: 8→16 | 確認: 8→16 |
| --------------- | ---------: | ---------: |
| 永続化漏れ      |      20→20 |      20→20 |
| 重複処理        |      20→20 |      20→20 |
| 3回目のリトライ |      20→20 |      20→20 |
| 配信順序の無視  |      14→12 |      17→16 |
| drop の無視     |      14→17 |      10→17 |

確認用で drop の無視は7 seed の追加検出。配信順序では2 seed の追加検出と3 seed の見逃しがあり、合計1件後退した。正常版の reset 数中央値は57→31。drop の初回検出までの操作数中央値は282→131だが、最初の反例の操作数中央値は6.5→11に伸びた。実時間中央値は両方約0.64msで、この小さい例から実環境の性能差を結論しない。

## 判断

履歴長16への一律変更は採用しない。長い履歴は drop 無視の追加検出に役立つが、短いケースを減らすことによる後退と、診断する履歴の長さが増すことを確認した。

次は8操作と16操作のケースを交互に使う仮説を、同じ512操作予算で評価する。確認用 seed 21〜40は既に結果を見たので再利用せず、41〜60を予約する。新しい plan を実行前に記録する。
