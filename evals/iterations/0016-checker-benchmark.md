# tla-ts・TLC・modelt の速度比較

同じ11モデルを完全探索し、全サンプルで正常終了・状態数・生成数が一致した。起動込みの中央値では modelt native が11件すべてで速かった。API再利用時は native が9件、Wasm が8件で tla-ts を上回った。関数更新と小さいfairnessモデルには、tla-tsの中央値が速い条件が残る。

[事前計画](../plans/0016-checker-benchmark.md)を先にコミットし、実装を `719d6748f9ec62f5576cc03da10edfeb01c33b6d` に固定した。測定開始時のworking treeはclean。source fingerprintは `0403ee47712888033bcac794c563965d31df5bfb00ce00cfee552cf89218049d`。検査器の実装は変更していない。

## 環境と比較範囲

- Apple M5、10 cores、32 GiB RAM、macOS 26.6.2。Node v24.22.2、Rust 1.98.0、arm64。
- tla-ts 0.0.10。`version=1.7.4`、`workers=1`、`livenessCheck=final`。
- TLC v1.7.4のjar。表示はTLC 2.19 rev `5a47802`。Temurin 21.0.13+9のarm64 JRE、1 worker、seed 16、ParallelGC。
- heapは各ツールの既定値。TLCログでは7,282 MB heap、64 MB offheap、MSBDiskFPSet、DiskStateQueue。メモリ予算や保存方式を共通化した測定ではない。
- modeltの上限はdepth / statesが2,000,000、workが20,000,000。全入力が上限内でcompleteとなった。
- OSキャッシュは消していない。起動込みはプロセス生成の費用を含むが、cold diskや初回インストールの測定ではない。Wasm列はNode上の実行であり、ブラウザの速度は未測定。

TLCログの`x86_64`をCPU種別として読んだ初期説明は誤りだった。v1.7.4の[TLCRuntime.getArchitecture](https://github.com/tlaplus/tlaplus/blob/v1.7.4/tlatools/org.lamport.tlatools/src/util/TLCRuntime.java#L147)は64-bit JVMにこのラベルを返す。`file`と`os.arch`では旧JREも今回のJREもarm64だった。以前の結果との差をRosetta解消の効果として扱わない。

これは対応済みの有限fragmentで、表現・探索器・GC・保存方式・frontendを含むツール全体を比較した結果。TLCの探索中liveness検査とtla-tsのfinal検査など内部方針の差は残る。既存の複合値・scalarモデルを使っており、TLA+全体、大規模な分散システム、並列探索の速度を示す値ではない。

## 証拠と再実行

[本測定](../runs/0016-checker-performance/result.json)には、ウォームアップを含む693サンプルを保存した。集計対象は539サンプル。生ログ・入力・全サンプル・環境・binaryのSHA-256は[manifest](../runs/0016-checker-performance/manifest.json)と[benchmark](../runs/0016-checker-performance/benchmark.json)から確認できる。[replay](../runs/0016-checker-replay/result.json)はdigestとsource / binaryを確認し、11入力を起動込み4経路・再利用3経路の計77回再実行した。全結果が再現した。replayを独立した性能サンプルに加えていない。

[検証ログ](../runs/0016-verification/result.json)に`just check`、`just browser`、`just safety-test`、`just checker-bench-test`、`just evaluate`、`just replay-evaluation`と測定・replayの終了結果を保存する。新しいハーネスの4テストは、bounded / empty / missing counts / count mismatchの拒否、集計、固定corpus、経路順を検査する。

同じsource fingerprintのcheckoutで、同じjarとJRE配布物を用意して実行する。JREは[Temurin 21.0.13+9の公式配布](https://github.com/adoptium/temurin21-binaries/releases/tag/jdk-21.0.13%2B9)。arm64 macOS JREのtar.gzはSHA-256 `225bab0a09491ef06835488cd942f5d2befa9a0410a2484f0c8bbcf7506ec09a`。実行用binaryのSHA-256はmanifestに保存した。出力先は毎回新しいディレクトリを指定する。

```sh
just checker-bench "$java" "$jar" "$jre_archive" evals/runs/new-checker-run
just checker-bench-replay "$java" "$jar" "$jre_archive" evals/runs/new-checker-run evals/runs/new-checker-replay
```

常駐nativeと再利用Wasmを繰り返し検査の経路として維持する。次の性能改善は、関数更新とfairnessをプロファイルしてから個別に評価する。
