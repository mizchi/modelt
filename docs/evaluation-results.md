# 初回の手法評価

2026-11-14。目的は「動くこと」から「追加で役に立つこと」へ評価軸を変えること。[事前の計画](evaluation-plan.md) に従い、意図的に入れた7種類の故障と正常版を比較した。実プロジェクトの未知バグ発見実績ではない。

実験は `just evaluate`、証拠の再生は `just replay-evaluation`。[集計](evaluation/pilot-2026-11-14/summary.json)、[探索の全試行](evaluation/pilot-2026-11-14/search.csv)、[PBT の全試行と反例](evaluation/pilot-2026-11-14/pbt.csv)、[実装で再現する witness](evaluation/pilot-2026-11-14/witnesses.json) を保存した。時間は macOS / arm64 / Node 24.22.2 での記述的な測定値。

## 現時点の採用候補

| 手法                            | 得られた知見                                                             | 提案                                                      |
| ------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------- |
| BFS の代表 witness              | モデルを探索し切っても3回目のリトライと drop 無視を見逃す                | モデルの不変条件検査に使い、実装には履歴探索を併用        |
| 有効操作のランダム walk         | 同じ512操作予算で既知の履歴依存故障を追加検出                            | 安価な比較基準として使う                                  |
| 状態・遷移の novelty corpus     | 全体として uniform より検出・到達遷移が少ない                            | この方式の既定採用を保留                                  |
| PBT + shrinking                 | 2〜5操作の再現可能な説明を生成。生成器の違いで検出率と費用が大きく変わる | 診断・縮小に使う。有効操作生成を実対象でも試す            |
| 仮想時計                        | 期限ちょうどの誤判定を即時・決定的に再現                                 | 時間依存の対象には時計の注入境界を設ける                  |
| 制御スケジュール + 履歴 checker | 逐次 await では出ない lost update を再現・拒否                           | 並行 API の評価を続ける。checker は実験モジュールに留める |
| SMT で同じ時刻境界を生成        | 手書き境界値と同じ故障を検出。追加の故障検出はない                       | 単純境界での常時利用は保留。複数制約の問題で再評価        |

これは用途を限定した提案で、パッケージの public API 追加や各手法の全面採用は行っていない。metamorphic testing、source mutation、native fuzzing、TLA+ / ITF 連携の追加価値は今回比較していない。統合テスト済みという理由だけで採用決定とはしない。

## モデルを網羅しても実装の履歴は網羅しない

counterModel は56状態・432遷移で探索が閉じ、433 witness を再生した。故障版ごとに2153回の reset/step を使い、永続化漏れ、重複処理、配信順序の無視を検出した。しかし3回目だけ重複適用する実装と、drop を無視する実装を見逃した。

3回目のリトライでは、モデルの状態は1回目以降変わらない。BFS は既訪問状態へ戻る履歴を延長しないため、実装の試行回数に依存する故障に届かない。drop 無視も、モデルのキューが空に戻った後の実装に残るメッセージを、後続操作で区別する必要がある。**モデルの状態を覆う witness と、実装の隠れた状態を区別するテスト集合は異なる。**

この差は手順の確認だけでなく、実際のモデル比較と正常版への再生で確認した。今後のモデル生成テストは、状態網羅に加えてリトライ回数・クラッシュ前後・モデル状態への再訪問を含む履歴を扱う。

## 同一予算の探索比較

seed 1〜20、各512回以下の reset/step、1ケース最大8操作。各 seed・手法には同じ正常版と故障集合を渡し、探索器は故障条件を参照しない。数値は検出した seed 数で、一般のバグ発見確率の推定ではない。

| 故障            | uniform walk | novelty corpus | uniform のみ | novelty のみ |
| --------------- | -----------: | -------------: | -----------: | -----------: |
| 永続化漏れ      |        20/20 |          14/20 |            6 |            0 |
| 重複処理        |        20/20 |          20/20 |            0 |            0 |
| 3回目のリトライ |        20/20 |          13/20 |            7 |            0 |
| 配信順序の無視  |        14/20 |           6/20 |           10 |            2 |
| drop の無視     |        14/20 |           0/20 |           14 |            0 |

正常版の誤検出、無効操作、再現失敗はいずれも0。到達した遷移数の中央値は uniform が173、novelty が62.5だった。novelty の2 seed に配信順序の追加検出はあるが、別の seed では見逃しが増えている。混合による価値はまだ比較していない。

この小さい novelty 実装は、既知の prefix に1操作追加し、新しいモデル状態・遷移の prefix を保存する。reset と prefix の再生が増え、正常版のケース数中央値は uniform の57に対して101。同じ SUT 操作予算でも、実際に生成したモデル遷移数の中央値は455に対して101。モデルの遷移が高価な場合には、別のコストモデルで再評価する余地はある。

これはモデルの状態・遷移のみを使う実装の結果。[Fest](https://www.usenix.org/conference/nsdi26/presentation/li) が使う因果順序の多様性、記録した選択列の変更、シナリオへの近さを評価した実験ではない。Fest 自体の否定や再現実験として扱わない。

## PBT は生成器と縮小の費用を含めて評価する

同じ20 seed、最大8操作、64試行で比較した。raw は操作配列を生成して無効操作を棄却する。enabled は整数の選択列から、その状態で実行可能な操作を生成し直す。enabled は初回の棄却率を見て追加した探索的実験。生成分布も変わるため、棄却削減だけを検出率の差の原因とは断定しない。

| 故障            |   raw | enabled | 縮小後の操作数中央値 |
| --------------- | ----: | ------: | -------------------: |
| 永続化漏れ      |  9/20 |   18/20 |                    3 |
| 重複処理        | 20/20 |   20/20 |                    2 |
| 3回目のリトライ | 13/20 |   16/20 |                    3 |
| 配信順序の無視  |  4/20 |   10/20 |                    4 |
| drop の無視     |  3/20 |    3/20 |                    5 |

正常版の無効入力の棄却数中央値は132から0、reset/step 数中央値は410から307.5へ減った。正常版の誤検出はなく、検出した反例はすべて故障版で再現し、正常版で通過した。

一方、3回目のリトライの比較では、縮小も含む reset/step 数中央値が339から851へ増えた。PBT の「試行数64」は生成・棄却・縮小・再確認を含む SUT 操作予算ではない。512操作予算の walk と直接の優劣を結論しない。縮小が作る短い説明の価値と、発見までの探索効率を別に測る。

## 時計と並行実行の制御

TTL では「期限以上なら失効」という契約に対し、実装を `now > expiresAt` にすると、期限ちょうどに古い値を返す。時刻を進めない workload は通過し、仮想時計で期限まで進めると失敗する。正常版は通過する。この実験は現実の時計で待つ方式との速度比較ではなく、期限へ到達させる可制御性の確認である。

同じ契約から Z3 に `elapsed = ttl` を与えても検出できたが、`ttl = 1, elapsed = 1` を直接与えた場合に追加する知見はなかった。記録した1実行では手書き境界の両版検査が約0.16ms、Z3 の初期化が約81ms、最初の solve が約102ms。統計的な性能比較ではない。ソルバーの必須化は、単純境界で得られる利点からは正当化できない。

非同期カウンターは read と write の解決順を実際の Promise で制御した。逐次実行では故障版も通過するが、2呼び出しの6通りの有効順序のうち4通りで、両方が同じ値を返す lost update を生じた。履歴 checker はこの4通りを拒否し、正常版の6通りは受理した。保存した順序と履歴はすべて再現した。

checker の予算切れは `inconclusive`。完了操作の履歴だけを扱い、未完了操作やクラッシュをまたぐ一貫性は未評価。加算カウンターの小さい履歴192通りでは、独立した必要十分条件と一致した。汎用 checker としての適格性は、既存 checker との差分テスト等で別途確認する。

## 次の判断材料

今の結果からは、入力の有効性、時計・実行順の可制御性、短い再現例を優先する。モデルの新規状態を増やすだけの探索や、単純境界への SMT 常時利用は既定採用しない。

次は実リポジトリの過去バグについて、故障 revision と修正 revision、固定した契約、同じ workload で再現する。対象は retry / timeout / queue / transaction のいずれかを持つ小さいライブラリから選ぶ。その後、修正を見ずに用意したケースで追加検出を測る。モデル作成・Driver 作成・反例の調査に要した人手も記録し、有効性の判断に含める。
